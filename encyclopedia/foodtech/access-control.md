## 한눈에 보기

사용자 인증과 역할 권한은 시스템 관리자, 외식업주, 레시피 담당자, 현장운영자와 조회자가 수행할 수 있는 작업과 접근 가능한 매장을 제한하는 기능이다. 화면뿐 아니라 API, 다운로드와 데이터 조회에 같은 정책을 적용한다.

## 왜 이렇게 정했는가

레시피 승인, 실제값 입력과 시스템 설정은 책임이 다른 작업이다. 하나의 넓은 권한으로 묶으면 실수나 권한 남용이 발생할 수 있고, 여러 매장의 데이터를 운영할 때 다른 매장 정보가 노출될 위험도 있다.

그래서 역할별 최소권한과 매장 범위 격리를 함께 적용한다. 브라우저가 보낸 역할이나 매장 식별자를 신뢰하지 않고 서버의 인증정보로 다시 판단한다.

## 무엇을 하는가

- 사용자 로그인과 계정 활성 상태를 확인한다.
- 역할별 조회·등록·수정·검토·승인·관리 권한을 평가한다.
- 매장 소속과 접근 가능한 데이터 범위를 제한한다.
- 화면, API와 다운로드에 같은 권한정책을 적용한다.
- 인증 실패와 접근 거부를 구분하여 기록한다.
- 계정과 역할 변경을 감사이력에 남긴다.

## 어떻게 동작하는가

1. 사용자가 자격정보로 인증한다.
2. 서버가 계정 상태, 역할과 매장 소속을 조회한다.
3. 요청한 리소스와 작업에 필요한 권한을 확인한다.
4. 데이터 쿼리에 허용된 매장 범위를 강제한다.
5. 허용된 요청만 실행하고 거부 결과도 기록한다.
6. 관리자가 역할과 소속을 변경하면 이후 요청부터 새 정책을 적용한다.

## 예외와 경계

- 클라이언트가 전달한 역할과 매장 ID만으로 접근을 허용하지 않는다.
- 직접 URL이나 API 호출로 화면 제한을 우회할 수 없게 한다.
- 레시피 작성, 검토와 승인 권한을 필요에 따라 분리한다.
- 비활성 계정과 권한 부족을 정상 오류로 처리하되 민감한 내부정보는 노출하지 않는다.
- 비밀값 원문을 일반 관리자 권한으로 조회하게 하지 않는다.

## 현재 결정

모든 화면, API, 다운로드와 데이터 조회에 역할 기반 접근제어와 매장 격리를 적용한다. 계정·역할 관리는 시스템 관리자, 레시피 승인은 별도 권한을 받은 담당자에게 제한한다.

구체적인 권한 매트릭스, 세션·토큰 방식, 비밀번호 정책과 다중 매장 사용자의 전환 UX는 설계 단계에서 확정한다.
