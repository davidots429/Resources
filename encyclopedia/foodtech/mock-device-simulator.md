## 한눈에 보기

Mock 장비 데이터 시뮬레이터는 실제 조리로봇과 주방장비 없이도 수집, 표준화, 장애복구와 전체 업무 흐름을 반복 시험할 수 있도록 가상 장비 이벤트를 만든다. 생성 데이터는 실제 제조사 데이터와 명확히 구분한다.

## 왜 이렇게 정했는가

개인 프로젝트에서는 실제 장비를 사용할 수 없지만, 정상 데이터만 담은 단순 샘플 파일로는 연결 단절, 중복, 인증 실패와 제조사별 표현 차이를 검증할 수 없다. 그렇다고 공개되지 않은 제조사 통신규격을 추정하면 실제 호환 구현으로 오해될 수 있다.

따라서 장비 유형, 연계 방식, 데이터 형식을 조합한 가상 프로파일을 만들고, 서로 다른 표현 성향을 가진 세 제조사 fixture를 적용한다. 이 방식은 실제 제품을 모방하기보다 어댑터와 표준화 기능이 다양한 입력 차이를 처리하는지 확인하는 데 목적이 있다.

## 무엇을 하는가

- 기본 장비, 볶음·교반 장비와 콤비오븐 데이터를 생성한다.
- REST, OPC UA와 MQTT 방식의 가상 연결을 제공한다.
- JSON, XML, CSV와 UA Binary 계열 입력을 재현한다.
- camelCase·중첩 구조, snake_case·평면 구조와 PascalCase·혼합 구조를 구분한다.
- 온도, 시간, 속도, 시각, Boolean, Null과 상태 코드 차이를 만든다.
- 정상, 오류, 연결 단절, 재연결, 중복, 인증 실패와 인코딩 오류를 시나리오로 실행한다.
- 같은 시드로 같은 이벤트를 다시 만들 수 있게 한다.

## 어떻게 동작하는가

1. 21개 프로파일 계열 중 연계 방식, 장비 유형과 데이터 형식을 선택한다.
2. `vendor-a`, `vendor-b`, `vendor-c` 표현 규칙 중 하나를 적용한다.
3. 프로파일과 fixture 조합에 불변 인스턴스 ID를 부여한다.
4. 정상 스키마에 맞는 이벤트를 생성하고 원천 스키마를 검증한다.
5. 어댑터 처리 후 제조사 중립 표준 스키마를 다시 검증한다.
6. 오류 데이터는 정상 스키마를 바꾸지 않고 별도 시나리오에서 생성한다.

각 생성 항목은 공개자료로 확인된 값, 표준에서 도출한 값, 추론한 값과 시험용 합성 값을 구분한다. 이 분류를 두는 이유는 Mock 값이 실제 제조사 사양처럼 사용되는 일을 막기 위해서다.

## 예외와 경계

- 실제 제조사 장비나 API와의 호환성을 주장하지 않는다.
- 제어 명령과 Method 호출을 생성하지 않는다.
- 공개되지 않은 I-Robo 2 연계 규격을 추정하지 않는다.
- 비정상 데이터 때문에 정상 데이터 스키마를 완화하지 않는다.
- OPC UA Binary의 상세 검증 방식은 설계에서 확정한다.

## 현재 결정

프로파일은 REST 6개, OPC UA 6개, MQTT 9개로 총 21개다. 각 계열에 세 fixture를 적용하여 최소 63개 인스턴스를 만든다. 제조사 중립 정보모델은 OPC UA 30200을 기본으로 하고 DIN/TS 18898:2021-09를 보완 자료로 사용한다.

REST는 HTTPS GET Polling, MQTT는 MQTT 5.0과 QoS 1, OPC UA Binary는 UA-TCP의 Browse·Read·Subscription, OPC UA JSON은 HTTPS Session-less Browse·Read를 사용한다. 세부 endpoint, topic, 보안 파라미터와 UA Binary 검증 방식은 설계에서 정한다.
