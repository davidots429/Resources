이 백과는 고객에게 제출하는 산출물과 역할이 다르다. 산출물이 승인과 검증의 기준이라면, 백과는 새 팀원이 현재 설계와 작업 방법을 이해하고 변경 과정을 이어받는 공간이다. 문서는 배경 지식이 없는 독자가 이 페이지에서 출발해 필요한 하위 문서와 원본 자료를 찾을 수 있도록 쓴다.

## 페이지의 시작과 범위

제목 아래에는 해당 개념의 뜻, 프로젝트에서 맡는 역할, 현재 구현 또는 설계 상태를 설명한다. 독자가 알아야 할 용어가 나오면 [용어 사전](glossary.md)이나 개념 문서에 링크한다. 상위 문서는 하위 항목의 목록이 아니라 업무 흐름·경계·선택 이유를 먼저 설명하고, 그 설명 중에서 상세 문서로 연결한다. 하위 문서는 자신의 상위 맥락으로 되돌아갈 수 있어야 한다. `data.md → data/`, `cooking.md → cooking/`, `ai.md → ai/`, `operations.md → operations/`의 경로도 이 관계를 드러낸다. 분류는 탐색을 돕되 교차 기능의 링크까지 막는 엄격한 분류 체계로 만들지 않는다.

`한눈에 보기`, `무엇을 하는가`, `어떻게 동작하는가`, `왜 이렇게 정했는가`, `현재 결정`, `최신 설계 반영`을 모든 페이지에 반복하지 않는다. 결정 이유는 해당 설계나 동작을 설명하는 문단에 함께 쓴다. 본문의 절은 `수집 경로`, `순번 복원`, `운영자 검토`처럼 실제 내용을 나타내는 이름을 사용한다.

입력·출력의 대응, 단계별 흐름이나 구성요소의 관계가 문장만으로 이해하기 어려우면 최신 산출물에 근거해 표·이미지·다이어그램을 사용한다. 시각 자료는 본문 설명을 보완해야 하며, 그림만 보아야 의미를 알 수 있는 정보는 문장으로도 설명한다. 산출물의 도식을 다시 그렸다면 원본과 현재 설계가 일치하는지 확인하고 해당 설명에 출처 각주를 붙인다.

## 사실과 상태

현재 효력이 있는 최신 [분석·설계 산출물](artifacts.md)과 원 프로젝트의 `AGENTS.md`, `pending_decisions.md`를 대조한다. 승인된 정책, 제안 단계 설계, 구현에서 검증된 사실, 미결정 사항을 구별한다. 특히 화면 코드·API 경로·물리 키·임계치가 설계안에만 있으면 실제 동작처럼 쓰지 않는다. 확인하지 못한 내용은 `확인 필요`, 후속 결정이 필요한 내용은 `보류`로 표시하고 결정 시점을 덧붙인다.

원본의 사업 요구와 개인 프로젝트의 선택이 다르면 두 맥락을 설명한다. 실제 장비를 쓰지 않는 Mock, 읽기 전용 연계, AI 권고의 사람 검토 같은 경계는 생략하지 않는다. 이전 버전의 서술을 본문에 누적하지 않는다.

## 링크와 각주

관련 개념은 문장 안에서 표준 Markdown 링크로 연결한다. `[[문서명]]` 같은 전용 문법은 사용하지 않는다. 원본 산출물이나 외부 자료가 주장·수치·선택의 출처라면 그 문장에 각주를 붙인다. 각주는 해당 문서의 버전과 접근 가능한 자료실 링크를 가리키고, 외부 자료는 원문 URL과 확인 대상을 적는다. 각주를 단순한 요구사항 ID 목록으로 만들지 않는다.

예를 들어 “수집은 장비를 제어하지 않는다.[^scope]”처럼 쓰고 페이지 하단에 다음을 둔다.

[^scope]: [요구사항 정의서 RD v0.7](/Resources/foodtech/files/Foodtech_AI_Recipe_Agent_RD_v0.7.docx), 시스템 범위와 제외 범위.

`[프로젝트 백과](README.md)` 또는 하위 폴더에서의 `../README.md`는 전체 진입점으로 이동할 때만 사용한다. 상세 설명을 대신하려고 `README.md#...` 우회 링크를 만들지 않는다. 상세 문서는 자기 영역의 상위 문서와 관련된 다른 기능을 직접 연결한다.

## 기록 문서

[문제 해결 기록](troubleshooting.md)은 증상, 재현 조건, 확인한 원인, 수정과 검증을 남긴다. [회의·결정 기록](meeting-notes.md)은 실제 논의의 날짜·참여자·결론·후속 작업만 기록한다. 회의가 없었다면 회의록을 만들어 내지 않는다. 공개할 수 없는 인증정보와 개인 데이터는 기록하지 않는다.

기능의 의미나 책임이 바뀐 경우에만 본문 맨 끝에 `변경 이력`을 둔다. 최초 작성, 최신 결정의 첫 반영, 오탈자 교정은 변경 이력에 넣지 않는다.

## 새 팀원 검토

새 페이지를 작성하거나 고칠 때 다음을 실제 독자 관점에서 확인한다.

1. 이 페이지 하나로 주제와 현재 상태를 설명할 수 있는가?
2. 모르는 용어, 상위 맥락, 다음에 읽을 문서로 이동할 수 있는가?
3. 결정을 내린 이유와 아직 검증하지 않은 부분이 문장에 드러나는가?
4. 수치·설계·외부 사실의 각주가 최신 원본을 가리키는가?
5. 실행 절차가 있다면 현재 저장소에서 재현 가능한가?
