## 목적

백과는 프로젝트의 기능을 처음 접하는 사람이 기능의 목적, 동작, 경계와 결정 이유를 한 문서에서 이해하도록 돕는다. 분석 산출물을 그대로 복제하지 않고 서로 흩어진 요구사항과 결정을 기능 단위로 연결한다. 상세 근거와 추적 정보는 자료실의 원본 산출물에서 확인하도록 분리하여 백과 본문은 기능 설명에 집중한다.

## 기준 자료와 최신성

현재 기본 기준 자료는 RD v0.4, SRS v0.4, DCD v0.3, `AGENTS.md`, `pending_decisions.md`다. 백과 본문은 항상 이 자료들의 최신 상태를 설명한다.

기능의 배경, 원래 요구 또는 결정 이유가 기본 기준 자료만으로 충분히 설명되지 않으면 입찰공고문, 과업지시서와 제안요청서 원본 PDF를 추가로 확인하여 보충한다. 원본 PDF를 항상 반복해서 요약하지 않고 필요한 경우에만 확인하는 이유는 최신 분석·결정 내용을 중심으로 서술하면서도 원래 요구의 맥락을 잃지 않기 위해서다.

자료 사이에 표현 차이가 있으면 다음 원칙을 적용한다.

1. 승인·부분 승인·보류 상태는 최신 `pending_decisions.md`와 `AGENTS.md`를 확인한다.
2. 고객 관점의 범위와 목적은 RD를 따른다.
3. 시스템 동작과 검증 가능한 상세는 SRS를 따른다.
4. 데이터 항목, 수집 조건, 매핑과 품질 판정은 DCD를 따른다.
5. 배경과 원래 요구를 보충할 필요가 있으면 입찰공고문, 과업지시서와 제안요청서 PDF를 확인한다.
6. 충돌을 발견하면 임의로 합치지 않고 본문에 `확인 필요`로 표시한다.

이 순서를 정한 이유는 문서의 역할이 서로 다르며, 결정 상태와 상세 정의를 한 자료만으로 판단하면 최신 결정이나 보류 조건을 놓칠 수 있기 때문이다.

## 기능 중심 분류

최상위 분류는 프론트엔드·백엔드·데이터베이스 같은 구현 계층이 아니라 시스템이 제공하는 기능을 기준으로 한다. 한 기능이 여러 기술 모듈을 사용하더라도 사용자의 목적이 같으면 같은 문서에서 설명한다.

기술 세부사항은 해당 기능을 이해하는 데 필요한 범위에서만 포함한다. 기술 선택 자체가 중요한 결정이면 별도 개념 문서로 만들고 관련 기능에서 연결한다. 이 기준을 택한 이유는 백과가 설계서의 복사본이 되는 것을 막고 기능 간 탐색을 쉽게 하기 위해서다.

## 문서 구성

각 기능 문서는 다음 순서를 기본으로 한다.

1. `한눈에 보기`: 기능의 목적과 현재 상태
2. `왜 이렇게 정했는가`: 요구, 제약, 대안과 선택 이유
3. `무엇을 하는가`: 사용자 관점의 기능 범위
4. `어떻게 동작하는가`: 입력부터 결과까지의 흐름
5. `예외와 경계`: 실패 처리, 제외 범위와 자동화하지 않는 부분
6. `현재 결정`: 확정·부분 승인·보류 사항
7. `관련 기능과 개념`: 다른 Markdown 문서로 이동하는 링크
8. `변경 이력`: 과거에 공개된 설명에서 실제로 달라진 내용이 있을 때만 기록

모든 문서에 같은 항목을 억지로 채우지는 않는다. 다만 `왜 이렇게 정했는가`는 생략하지 않는다. 요구사항 ID, 산출물 코드와 출처 목록을 모은 별도의 `근거` 항목은 작성하지 않는다.

## 결정 이유 작성 규칙

결정 이유는 다음 내용을 구분하여 쓴다.

- 요구된 이유: 고객 요구나 상위 목적
- 제약에 따른 이유: 실제 장비 미사용, 읽기 전용, 예산, 일정, 보안 같은 조건
- 선택 이유: 후보 중 현재 방식을 택한 근거
- 남은 불확실성: 아직 확정하지 않은 값과 결정 시점

확인되지 않은 이유를 그럴듯하게 만들지 않는다. 문서에서 직접 확인되지 않는 해석이 필요하면 `해석`이라고 표시하고, 설계에서 확인해야 하면 `보류`로 남긴다. 독자가 상세 근거나 추적 정보를 확인해야 하는 경우에는 자료실의 원본 산출물을 안내한다.

## 링크 규칙

링크는 표준 Markdown 상대 링크를 사용한다. 예를 들어 `[장비 데이터 수집](device-data-collection.md)`처럼 작성한다. 렌더러가 정해지기 전에는 `[[문서명]]`과 같은 전용 위키 문법, 플러그인 문법이나 프런트매터에 의존하지 않는다.

표준 Markdown 링크를 택한 이유는 GitHub 자체 미리보기에서도 동작하고, 다음 단계에서 어떤 정적 사이트 생성기를 선택하더라도 변환 부담이 작기 때문이다.

## 변경 이력 규칙

본문은 과거 설명을 누적하지 않고 현재 상태만 직접 서술한다. 변경 이력을 기록할 필요가 있으면 현재 서술과 섞지 않고 문서의 모든 본문이 끝난 뒤 최하단에 독립된 `변경 이력` 절로 둔다. 변경 이력에는 날짜와 변경 내용만 기록하며 근거 열이나 근거 항목을 두지 않는다.

최초 작성과 현재 결정의 단순 반영은 변경 이력이 아니다. 이미 공개된 기능의 의미, 책임, 범위 또는 중요한 결정이 이후 달라졌을 때만 변경 이력을 추가한다. 오탈자 수정과 문장 다듬기도 기록하지 않는다.

이 방식을 택한 이유는 현재 기능 설명과 과거 변화 기록을 명확히 분리하여 독자가 변경 이력을 읽지 않아도 현재 상태를 이해할 수 있게 하면서, 필요한 경우에는 중요한 결정 변화도 추적할 수 있도록 하기 위해서다.
