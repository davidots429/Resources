## 한눈에 보기

수집 상태 모니터링은 장비별 연결상태, 최종 수신시각, 지연과 오류를 보여주고 통신 장애 후 데이터를 재처리하는 기능이다. 복구 과정에서 누락과 중복을 방지하고, 끝내 처리할 수 없는 데이터는 식별 가능한 격리 상태로 남긴다.

## 왜 이렇게 정했는가

실시간 수집은 네트워크와 장비 상태에 영향을 받으므로 일시적인 장애를 완전히 피할 수 없다. 장애를 단순 실패로 끝내면 데이터가 사라지고, 무조건 다시 저장하면 중복이 생긴다.

그래서 임시저장, 멱등성 키와 처리 오프셋을 사용해 재처리하고, 사용자에게 데이터의 최신성과 연결상태를 보여준다. 플랫폼이 수신하지 못한 장비 내부 데이터는 플랫폼 손실과 구분한다.

## 무엇을 하는가

- 장비와 수집 프로파일의 연결상태를 표시한다.
- 최종 발생·수신시각과 지연을 계산한다.
- 오류 데이터를 임시 보관하고 재시도한다.
- 고유키와 오프셋으로 중복을 판정한다.
- 연결 복구 후 대기 데이터를 재처리한다.
- 실패건을 격리하고 관리자에게 알린다.
- 재처리 결과와 건수를 조회한다.

## 어떻게 동작하는가

1. 수집기가 연결과 처리 상태를 지속적으로 기록한다.
2. 오류가 발생하면 원천 메시지와 처리 위치를 임시저장한다.
3. 정책에 따라 제한된 횟수로 재시도한다.
4. 고유키와 오프셋을 확인해 이미 처리한 데이터를 건너뛴다.
5. 성공한 데이터는 정상 파이프라인으로, 최종 실패는 격리 영역으로 보낸다.
6. 현황판에 연결, 지연, 재처리와 오류 상태를 갱신한다.

## 예외와 경계

- 원천 장비가 장애 중 데이터를 보존하지 않은 경우 플랫폼이 복원할 수 있는 손실과 구분한다.
- 재시도 한도를 넘긴 데이터를 무한히 다시 보내지 않는다.
- 충돌한 데이터를 기존 정상 레코드 위에 덮어쓰지 않는다.
- `stale`과 `offline` 기준이 확정되기 전에는 임의 수치로 상태를 만들지 않는다.
- 재처리 승인은 운영자와 관리자 권한을 구분한다.

## 현재 결정

63개 Mock을 5초 간격으로 수집하며 정상 13건/초, 지속 최대 26건/초와 순간 100건/초를 시험 기준으로 사용한다. MQTT·OPC UA 수집 지연 p95 2초, REST 최신성 p95 조회주기+2초, 표준화 완료 p95 1초와 최신 화면 표시 10초 이내를 목표로 한다.

프로토콜별 retry, timeout, session과 재전송 세부 정책, `stale`·`offline` 전환 기준은 설계 단계에서 확정한다.
