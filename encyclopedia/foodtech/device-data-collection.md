## 한눈에 보기

장비 데이터 수집은 조리로봇과 주방장비의 상태, 설정, 조리 진행, 결과와 오류 정보를 읽어 플랫폼으로 가져오는 기능이다. 실시간 연계가 불가능하거나 실제 장비가 없는 경우에는 파일 업로드, 운영자 입력과 Mock 시뮬레이터를 같은 수집 체계 안에서 사용한다.

현재 프로젝트의 장비 연계는 읽기 전용이다. 플랫폼은 장비를 구동하거나 멈추지 않고, 설정값을 전송하거나 장비 프로그램을 배포하지 않는다.

## 왜 이렇게 정했는가

과업은 서로 다른 조리로봇과 주방장비의 데이터를 통합하여 레시피 추천과 운영 분석에 활용하도록 요구한다. 그러나 개인 프로젝트에서는 실제 장비를 사용하지 않으며, 제조사마다 공개하는 인터페이스와 데이터 항목도 다르다. 실제 규격을 추정해서 하나의 제조사 호환 구현처럼 만들면 검증하지 않은 내용을 사실로 오인할 수 있다.

따라서 실제 제품은 데이터 항목과 동작을 이해하기 위한 참조 대상으로만 사용하고, 수집 기능은 제조사 중립 표준 모델과 가상 제조사 fixture를 이용해 검증한다. I-Robo 2와 RATIONAL iCombi Pro를 주 참조 대상으로, BOTINKIT OMNI와 UNOX CHEFTOP-X를 보조 참조 대상으로 두며, OPC UA 30200을 제조사 중립 정보모델의 기본 기준으로 사용한다.

REST, MQTT와 OPC UA를 함께 다루는 이유는 특정 프로토콜 하나에 맞춘 수집기로는 제조사와 설치 환경의 차이를 검증하기 어렵기 때문이다. 파일과 운영자 입력을 대체 경로로 두는 이유는 제조사가 실시간 인터페이스를 제공하지 않거나 현장에서 네트워크 연계를 사용할 수 없는 경우에도 조리 결과와 실제 적용값을 남겨야 하기 때문이다.

## 무엇을 하는가

- 수집할 장비와 데이터 소스를 등록하고 연계 범위를 관리한다.
- REST Polling, MQTT, OPC UA 방식으로 읽기 전용 데이터를 수집한다.
- CSV, JSON, JSON Lines 파일과 운영자 입력을 대체 수집 경로로 제공한다.
- 모든 이벤트에 소스, 장비, 발생시각, 수신시각, 순번, 스키마 버전과 품질 상태를 연결한다.
- 연결 단절, 재연결, 중복 수신, 인증 실패와 인코딩 오류를 식별한다.
- 수집 상태와 최신 수신시각을 표시하고 필요한 데이터를 재처리한다.
- 원천 payload를 보존하여 이후의 [데이터 표준화와 코드 매핑](data-standardization.md) 결과를 추적할 수 있게 한다.

## 어떻게 동작하는가

1. 시스템 관리자가 데이터 소스와 수집 프로파일을 등록한다.
2. 수집 어댑터가 프로파일에 지정된 읽기 전용 방식으로 데이터를 받는다.
3. 플랫폼이 공통 메타데이터를 붙이고 원천 데이터를 보존한다.
4. 중복, 형식, 순번과 시각 관계를 우선 확인한다.
5. 수집된 데이터는 표준화와 품질 판정 단계로 전달된다.
6. 연결 장애가 발생하면 상태를 기록하고 재연결 후 누락과 중복을 확인한다.

실시간 Mock의 기본 규모는 63개 동시 인스턴스다. 정상 수집 간격은 인스턴스당 5초이며 정상 부하는 13건/초, 최대 지속 부하는 26건/초, 순간 버스트는 100건/초를 기준으로 한다. 이 값을 나눈 이유는 정상 운영, 장시간 고부하와 짧은 급증을 같은 지표로 취급하면 수집기의 병목과 복구 능력을 구분해 검증하기 어렵기 때문이다.

## 예외와 경계

- 장비 제어, 원격 구동, 설정값 전송과 프로그램 배포는 하지 않는다.
- 실제 제조사 API·SDK·통신규격으로 확인되지 않은 값은 제조사 사양으로 표현하지 않는다.
- 제조사가 제공하지 않는 데이터나 권한을 우회하여 수집하지 않는다.
- 비밀값, 실제 토큰과 인증서 값은 데이터 정의서나 백과에 기록하지 않는다.
- 파일은 UTF-8 CSV, JSON 또는 JSON Lines를 사용한다. 압축 해제 후 10 MB 또는 10,000레코드를 한도로 하며 gzip 스트림만 허용한다.
- 식별 가능한 일부 오류 레코드는 격리할 수 있지만 파일 수준 오류는 전체 파일을 거부한다. 이렇게 구분하는 이유는 정상 레코드를 불필요하게 버리지 않으면서도 파일 구조 자체를 신뢰할 수 없는 경우의 부분 적재를 막기 위해서다.

## 현재 결정

### 확정

- Mock 프로파일은 REST, OPC UA, MQTT와 JSON·XML·CSV·UA Binary 조합으로 구성한 21개 계열을 사용한다.
- 각 계열은 `vendor-a`, `vendor-b`, `vendor-c` fixture를 가지며 최소 63개 인스턴스를 만든다.
- REST는 HTTPS GET Polling과 OAuth 2.0 Client Credentials를 사용한다.
- MQTT는 MQTT 5.0, TLS, QoS 1과 Topic ACL을 사용한다.
- OPC UA Binary는 UA-TCP, SignAndEncrypt와 Browse·Read·Subscription을 사용한다.
- OPC UA JSON은 HTTPS 기반 Session-less Browse·Read 방식의 프로젝트 Mock 계약을 사용한다.
- 모든 연계는 읽기 전용이며 실제 제조사 호환성을 주장하지 않는다.

### 부분 승인 또는 보류

- REST의 세부 endpoint, timeout, retry와 rate limit은 설계 단계에서 확정한다.
- MQTT topic, retained message, session expiry와 재전송 처리는 설계 단계에서 확정한다.
- OPC UA SecurityPolicy, 인증서 수명주기, Subscription 파라미터와 재연결 처리는 설계 단계에서 확정한다.
- 소스별 `stale`·`offline` 전환 기준은 설계 단계에서 확정한다.

보류 항목을 임의로 채우지 않는 이유는 실제 성능시험과 보안 설계 없이 수치를 고정하면 구현과 검증 기준이 서로 어긋날 수 있기 때문이다.
