---
title: 산출물과 추가 문서
---

산출물은 고객에게 제공할 기준과 검증 가능한 약속을 기록한다. 백과는 개발자가 그 약속을 실제 기능과 작업 순서에 적용할 때 읽는 설명이다. 두 곳에서 같은 주제를 다뤄도, 공식 수치·ID·상태의 기준은 최신 산출물과 결정 기록에 있다. 모든 원본은 [자료실](/Resources/foodtech/files/)에서 다운로드한다.[^rules]

## 분석과 설계의 위치

| 문서 | 개발자가 먼저 확인할 질문 |
| --- | --- |
| RD v0.7 · SRS v0.7 | 왜 만들며 무엇을 구현·검증하는가 |
| DCD v0.6 | 어떤 출처를 누가 어떤 방식·주기로 수집하는가 |
| SAD v0.3 | 서비스·데이터·보안 경계는 어디인가 |
| Development Standards v0.4 | 코드·API·시험을 어떤 규칙으로 작성하는가 |
| IA/Storyboard v0.4 · UML Design v0.3 | 화면·사용자 흐름과 모듈 상호작용은 무엇인가 |
| ERD v0.2 · Table Definition v0.2 · Codebook v0.2 | 데이터 관계, 물리 저장 구조, 의미·단위·코드는 무엇인가 |

ERD, 테이블 정의서, 코드북은 별도 산출물이다. 예전의 통합 파일에 새 설계를 덧붙여 단일 기준처럼 사용하지 않는다. 각 문서의 `TBD`와 제안 단계 표기는 [현재 진행 상태](project-status.md)와 함께 읽는다.[^rules]

## 구현하면서 추가할 기록

현재 산출물에서 계획이나 설계로만 남은 내용은 실제 구현을 시작할 때 개발자 문서로 채워야 한다. 특히 제품 저장소의 실행 명령과 로컬 초기화, 확정된 API 요청·응답 예시와 오류 코드, 스키마·마이그레이션 절차, Mock fixture 실행법, 계약·통합·부하시험 결과, 배포·복구 runbook, 장애 사례가 필요하다. 아직 존재하지 않는 문서는 빈 페이지에 가짜 명세를 채우지 않고 관련 상위 페이지에서 보류 상태와 확정 시점을 밝힌다.

새 문서가 생기면 [개발 환경](development-setup.md), [API](api-reference.md), [데이터 모델](data.md), [문제 해결 기록](troubleshooting.md)에서 연결한다. 고객 산출물과 다른 내용이 확정되면 먼저 그 차이를 검토한 뒤 두 문서를 함께 갱신한다.

[^rules]: [요구사항·설계 문서 작성 규칙에 따른 현재 산출물](/Resources/foodtech/files/), 최신 버전과 문서별 역할.
